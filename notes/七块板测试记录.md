## 一·四、固件编译记录（Linux + arm-none-eabi，2026-11-02）

工具链：`arm-none-eabi-gcc 10.3.1`（Debian 包 `15:10.3-2021.07-4`）、`cmake 3.22.1`、`make 4.3`。本机 Linux 侧没装 openocd / st-flash / CubeProgrammer，烧录仍在 Windows 侧用 STM32CubeProgrammer。

构建类型统一 `Debug`（`-Og -g`），与 42 最早那次基线一致，这样三块板的体积可以横向比。

```bash
cd "<V2>/2.Firmware/dummy-35motor-fw"       # 或 dummy-ref-core-fw / dummy-42motor-fw
cmake -B ../build/motor35-baseline -DCMAKE_BUILD_TYPE=Debug
cmake --build ../build/motor35-baseline -j$(nproc)
```

路径含空格和中文，**引号必须加**。编译目录放在源码树外面（`../build/xxx`），因为 `CMakeLists.txt` 用 `file(GLOB_RECURSE "Core/*.*" ...)` 收源文件，在树里建 build 目录有被扫进源列表的风险。CMakeLists 里已写死 `set(CMAKE_C_COMPILER arm-none-eabi-gcc)`，不需要额外的 toolchain file。

### 为了能在 Linux 下编过，改了 6 处

|---|---|---|---|
| 35 | `UserApp/common_inc.h:8`、`UserApp/configurations.h:9` | `#include "stdint-gcc.h"` → `<stdint.h>` | `stdint-gcc.h` 是 GCC 私有头，当前 arm-none-eabi 的三个 include 搜索路径都不提供（全机只有 x86_64 宿主 GCC 带它）。42 侧 2026-09-06 已这样改过，35 保持上游原样所以编不过 |

### 两条要记住的容量约束

1. **电机板 Flash 不能涨到 95 KB 以上**。链接脚本 `STM32F103CBTx_FLASH.ld` 把整片 128 KB 都给了代码，没为 `0x08017C00` 起的 32 KB 编码器标定区留保留段。代码越过 95 KB（偏移 97 280 B）会静默覆盖标定数据。现在 74.5 KB，余 22.2 KB。
2. **REF 的 CCMRAM 已经用满 100%**。`configTOTAL_HEAP_SIZE = 65536` 的 FreeRTOS 堆 `ucHeap` 恰好填满 64 KB CCMRAM。以后往 `.ccmram` 段再放任何东西都会直接链接失败，得先调小这个堆。这不是 bug，本来就是这么设计的，但没有余量。

### 一个无害的编译警告

35 固件会报 `Ctrl/Sensor/Encoder/mt6816_base.h:42: warning: no return statement in function returning non-void`。35 的基类 `SpiTransmitAndRead16Bits` 是空实现（42 改成了纯虚），看着像隐患，但 `Port/mt6816_stm32.h` 两个方法都带了 `override`，签名不匹配照样编译报错，所以不存在"静默调到空函数"的风险。可以忽略。

## 一·四b、电机固件 CAN 死锁修复（2026-11-02）

烧 35 板和 REF 之前先改掉的。42 和 35 两份固件一起改，改完 `Core/Src/can.c` 与 `Core/Inc/can.h` 仍然逐字节相同。

### 原问题

`Core/Src/can.c` 有两处一失败就调 `Error_Handler()`，而 `Core/Src/main.c:171-179` 的 `Error_Handler()` 实现是 `__disable_irq()` + `while(1){}` —— **关节板永久卡死，只能断电重启**。

触发条件很日常：总线没接终端电阻、主控没上电、CAN 线序接错，都会让发送失败。配合 `AutoRetransmission = DISABLE` 更容易踩到。

### 改法

| 位置 | 原来 | 现在 |
|---|---|---|
| `CAN_Send()` | `HAL_CAN_AddTxMessage` 失败 → `Error_Handler()` | 先自旋等一个空发送邮箱（上限 `CAN_TX_SPIN_LIMIT = 2000` 次轮询），等不到就丢这一帧并 `canTxDropCount++` |
| `HAL_CAN_RxFifo0MsgPendingCallback()` | `HAL_CAN_GetRxMessage` 失败 → `Error_Handler()` | `canRxErrorCount++` 后直接 `return` |

接收那处要注意：原来**就算不死锁也不能往下走**，否则会把上一帧残留的 `RxHeader` / `RxData` 当成新帧处理，所以必须 `return` 而不是只去掉 `Error_Handler()`。

两个计数器是 `volatile uint32_t`，在 `can.h` 里 `extern` 出来了，可以用调试器看，也可以以后加条 CAN 命令读出来。

### 两个设计取舍

**为什么敢在中断里自旋**：`CAN_Send` 的全部 8 个调用点都在 `UserApp/protocols/interface_can.cpp`，由 CAN RX 中断（抢占优先级 **3**）触发；20 kHz 电机控制环在 TIM4 中断（抢占优先级 **0**）里，优先级更高，所以这段自旋不会拖慢控制环。

**为什么不用 `HAL_GetTick()` 做超时**：SysTick 的优先级低于 CAN RX 中断，`uwTick` 在这个 ISR 里根本不会递增，拿它做超时会变成死循环。所以用的是轮询次数上限，不是精确超时。

### 没动的地方

`MX_CAN_Init()` 里 `HAL_CAN_Init` 和 `HAL_CAN_ConfigFilter` 失败仍然进 `Error_Handler()`（can.c:69、87）。那是开机配置失败，确定性的、也确实该停住，不是运行期风险。

### 代价与遗留

- Flash +104 B，RAM +8 B（两个计数器）。
- `AutoBusOff = DISABLE` 意味着一旦进 bus-off 要靠软件恢复，**现在没有恢复逻辑**。这是另一件事，留作后续。
- 42-1、42-2 上烧的是修复前的固件，**需要用新 hex 重烧**。

## 一·四c、REF 固件：没接电机板时 OLED 不亮（CAN 发送死等，2026-11-02）

起因：看到别人的复刻视频说「REF 的 `main.cpp` 要先连上电机板，OLED 才会亮，把那行注释掉就行」。对照源码确认**说法成立**，但机制不是「等电机板连上」，而是 **CAN 发送卡死**。

### 卡在哪

`UserApp/main.cpp` 的 `Main()` 按顺序执行：`InitCommunication()` → **`dummy.Init()`** → 死等 MPU6050 → `oled.Init()`。卡在第二步：

1. `dummy.Init()` → `SetCommandMode(COMMAND_TARGET_POINT_INTERRUPTABLE)` → `SetJointAcceleration()` → 对 J1–J6 各调一次 `SetAcceleration()`，**连发 6 帧 CAN**。
2. `Bsp/communication/interface_can.cpp` 的 `CanSendMessage()` 每发一帧，先要 `osSemaphoreAcquire(sem_can1_tx, osWaitForever)`。这个信号量计数为 1，**只在发送成功回调 `tx_complete_callback()` 里释放**。
3. 总线上没有别的节点，就没人回 ACK。`AutoRetransmission = DISABLE`，帧发一次失败就结束（TERR）。HAL 只记错误码，**不调 TxMailboxCompleteCallback**；`tx_error()` 是空函数。
4. 第 1 帧拿走了信号量，信号量就再也还不回来。**第 2 帧永远等下去**，Main 任务挂起，OLED 永远不初始化。

这和 CubeProgrammer 暂停 3 次都停在 `prvIdleTask` 的现象一致（所有任务都在等）。**之前判断「Main 卡在等 MPU6050」是错的**：先卡住的是 `dummy.Init()`，MPU6050 的循环还在它后面。

这和一·四b 电机板的 CAN 死锁是同一类缺陷：发送失败没有出路。

### 改法（临时）

`UserApp/main.cpp` 第 163 行 `dummy.Init();` **已注释掉**，并加了注释说明原因（2026-11-02）。**还没重新编译、没烧录。**

- 不改固件也有办法：CAN 总线上接**任意一块通电的电机板**，有节点回 ACK 就不会卡。
- 代价：开机不会把关节加速度发给电机板。**接上机械臂前必须改回来**。根治应该给 `CanSendMessage()` 加超时，并在发送失败 / 中止时也释放信号量。
- 注释掉之后还有第二道关：`do { mpu6050.Init(); } while (!testConnection())`。U10（MPU6050）没焊好或 I2C 不通，OLED 照样不亮，下一步就去查 U10。
- 与 USB 不识别**无关**：USB 在 `Main()` 之前初始化，由单独的任务处理。USB 还是 J1 / D+ 的硬件问题。

## 二·六、42-3 维修记录：CAN 芯片 U5 和 STM32 被打坏（2026-11-01 ~ 11-02）

**结果**：电源部分已修复（拆掉坏的 U5，原 U7 焊回继续用），9 V 下 T2 = 3.3 V，电流 0.006 A。但烧录时发现 **STM32 也坏了**（见第 8 条）。**等新的 U5 和 STM32 到货一起换**。

### 1. 现象
| 时间 | 情况 |
|---|---|
| 上电前 | T2 对地 9.7 kΩ，和 42-1 一样，断电测试正常 |
| 9 V 上电 | T2 = **3.79 V**（应为 3.25~3.35 V） |
| 升到 24 V | T2 仍是 3.79 V；R13 / C16 / R14 那一片发烫 |
| 复测 | T1（5 V）= 5.27 V 正常，**T2 掉到接近 0 V** |
| 断电 | T2 对地 **0 Ω**（42-1 同一点 9.68 kΩ） |

供电方式：用 P1 测试插线供电，**插线上 CAN 两根线头没处理好**。

### 2. 用到的测试方法
- **同型号板对比**：拿 42-1 量同一个点
- **拆件隔离**：拆掉嫌疑元件，再量还短不短
- **灌电流找发热**：稳压电源 1.0 V、限流 0.5~2 A，从 T2 往 3.3 V 灌电，摸哪颗芯片发热
- **压降法**：灌电时万用表 2 V 档、黑笔接 C11 负极，逐个量 3.3 V 网络上 16 个点（[Motor42-3V3短路测点图.png](Motor42-3V3短路测点图.png)），电流流向短路点，**读数最低、或者比别处低的点**就是短路方向

### 3. 排查过程
| 步骤 | 做了什么 | 结果 | 当时的判断 |
|---|---|---|---|
| 1 | 断电量 T2 对地 | 0 Ω；上电前是 9.7 kΩ | 上电后有元件坏了，不是焊接连锡 |
| 2 | 拆 U7（LP2992） | 还是 0 | 短路不在 U7 |
| 3 | 1 V / 0.5 A 灌电，手摸 | 摸不出发热；电源电压显示 0 | 短路电阻极小，0.5 A 下发热太少 |
| 4 | 压降法 1 A，量 16 点 | C22 = 0，U5 第 3 脚 = 0.15 V，其余 0.207 V | ❌ 以为短在 C22 |
| 5 | 复核 C22 两个焊盘 | 重测：C22 的 3.3 V 端 = 0.207 V，GND 端 = 0 | **C22 没问题，第 4 步是表笔点到了 GND 那一端** |
| 6 | 重新看第 4 步 | 只有 U5 第 3 脚比别处低 57 mV（旁边 C36 是 0.207 V） | 电流在流向 U5 → **U5 击穿** |
| 7 | 限流加到 1.5~2 A 灌电 | **U5 发烫** | ✅ 确认 U5 |
| 8 | 拆 U5，旧 U7 焊回 | T2 对地 5.7 kΩ；9 V 下 T2 = 3.3 V；电流 0.006 A（42-1 带 U5 是 0.02 A） | 电源修好，U7 是好的，没有漏电 |

### 4. 最终解决办法
拆掉击穿的 **U5（SN65HVD232）**，原来的 U7 焊回继续使用。U5 暂时空着，等新芯片。

### 5. 原因分析
1. P1 第 2 脚是 +24V，第 3 脚是 CAN_L，两个脚紧挨着。测试插线的 CAN 线头没处理，**碰到了 +24V（当时 9 V / 24 V）**。用户说是 CAN 两根线碰在了一起；但 CAN_H 和 CAN_L 互碰不会烧芯片（SN65HVD232 能扛总线短路），所以一定还碰到了 +24V
2. 高电压从 CAN_L 进入 U5，再从芯片内部**倒灌进 3.3 V**。U7 是 LDO，只能往外送电流，不能往回吸，所以 T2 被顶到 3.79 V
3. 随后 U5 内部击穿，3.3 V 对地短路，T2 掉到 0；U7 带着短路发热（它自带限流和过热保护，所以没坏）
4. 那片「发烫」其实是 U7 在扛短路，R13 / R14 / C16 正常时只有 0.4 mA 电流，不会发热

### 6. 走过的弯路
- 第 4 步把 C22 的 GND 端当成 3.3 V 端量，误判为 C22 短路。**0402 两个焊盘只隔 1 mm，压降法读到 0 时一定要两端都量一次**

### 7. 经验
- **测试插线必须先把 CAN 两根（第 3、4 脚）从插头里挑出来或剪掉**（已写进指南 3.1）
- 3.3 V 这一路比 LDO 的固定输出还高 → 优先怀疑有别的电源在**倒灌**，不一定是 LDO 坏了
- 金属性短路（电阻接近 0）用小电流摸不出热，要加大电流或者用压降法

### 8. 烧录时发现 STM32 也坏了（2026-11-02）
| 步骤 | 做了什么 | 结果 |
|---|---|---|
| 1 | ST-Link 连接 42-3 | ❌「无法获取内核 ID / 未找到 STM32 目标机」。**同一根线、同一设置在 42-2 上能连**（0x410 / 128 KB，已烧录成功） |
| 2 | 连接时量 T2、C9（NRST）、R9（BOOT0） | 3.3 V / 3.3 V / 0 V，正常 |
| 3 | 断电蜂鸣 P3 第 2、3、1 脚 ↔ U3 第 37、34 脚、C11 负极 | 都通 |
| 4 | 二极管档 U3 第 34、37 脚（红笔接地） | 42-3 约 0.6 V，42-2 约 0.5 V，差别不大，SWD 脚没有明显击穿 |
| 5 | 频率 480 kHz + Under reset，镊子短接 C9 按住复位再连接 | 无效 |
| 6 | 通电量 U3 第 1、24、36、48 脚（VDD）、第 9 脚（VDDA）、第 23、35、47 脚（VSS）、第 8 脚（VSSA） | 全部正常 |
| 7 | 整颗 U3 加助焊剂重新拖焊 | 仍连不上 |

**结论**：**STM32（U3）内核已损坏**，也是同一次 24 V 事故造成的：高电压从 CAN_L 打坏 U5 后，很可能经 U5 和 STM32 之间的两根线（U3 第 32、33 脚）进入 STM32，同时 3.3 V 被顶到 3.79 V。电源部分没坏，所以当时电压、电流都量不出问题。
和 U5 没焊**无关**：SWD 是芯片自带的硬件功能，不依赖固件，空白芯片只要供电正常就能连上；U5 接的是第 32、33 脚，SWD 是第 34、37 脚。

| 8 | 断电二极管档量 D4 | 正向 0.1~0.3 V，反向 OL；方向也对 | ❌ 当时据此认为 D4 正常（**也被骗了**） |
| 9 | 放掉 C11 的电，重新逐级量 | D1、C11、D4 两端正常；C19 0、电流 0 | — |
| 10 | 量 R15 右、U6 第 5 / 4 脚 | 约 0.33 V | 和 D4 端读数矛盾 |

### 5. 最终解决办法
1. **STM32 全部引脚重新拖焊**，清掉第 47 / 48 脚附近的连锡
2. **更换 D4**（1N5819WS，SOD-323）

### 6. 原因分析
- **短路**：STM32 第 47 脚（VSS）和第 48 脚（VDD）之间连锡。这两个脚相邻、间距 0.5 mm，是 LQFP 最容易连锡的地方之一
- **D4**（用户分析）：D4 有色环那一端**虚焊**（或 D4 本身不良）。量「D4 下端」时表笔把 D4 压到了焊盘上，所以通电读数正常（8.4 / 8.6 V），断电蜂鸣、二极管档也都通过；不压的时候电送不到 U6，U6 输入只有零点几伏，U6 不启动，电流为 0。换件后正常
- 压降法第 1 步把矛头指向 R4、读到 0 的原因**没有完全弄清楚**，最可能是表笔误差（和 42-3 的 C22 类似）。R4 本身是好的

### 7. 走过的弯路（含我的错误）
- R4 上下两端说反了，导致一次错误分析
- 说「D4 在 U6 左下方」是错的：**D4 在 U6 左上方**（大 TVS 二极管 D2 左边），U6 左下方的是 **D3**
- 说「R15 在 U6 正下方」是错的：**R15 在 U6 上方**（丝印在 P2 旁边）
- 说 EN 应该约 8.6 V 是错的：**ME3116 的 EN 正常约 3.9 V**（35-1 实测 3.87 V）
- 用蜂鸣档、二极管档判断 D4「正常」：肖特基二极管正向压降小，蜂鸣档也会响；而且**表笔一压，虚焊就暂时接通**，所以这两个断电测试都没测出问题
- 拆下的旧 R4 没有量就丢了，少了一个判断依据

### 8. 经验
- 4 层板上 3.3 V 对地短路，**逐颗量去耦电容两端电压**最准：不受黑表笔接哪里的影响
- 一时找不到短路的话，可以**拆 0 Ω 电阻把几种地分开**，先确定短在哪一种地上
- **虚焊「压上去才通」**：要量焊盘的铜皮或者下游的点，不要只量元件的金属端；也可以通电时一边看下游读数，一边用牙签按元件
- 怀疑供电不稳时，**先用镊子短接 C11 放电再量**：C11 对地是 OL，充上电后几分钟都不会掉，会骗人
- 上电时**一定看电源屏幕的电流**：电流 0 说明后级根本没在工作
- 拿好板（35-1）量同一个点，是纠正错误预期最快的办法
- 拆下来的元件**先量再扔**

### 9. 备件消耗
- 1N5819WS：用掉最后一颗备件（采购 15 颗，需要 14 颗）
- NTC（R4）：用了一颗新的，旧的已丢

## 六、排障方法总结（从 42-3、35-2 学到的）

### 电源对地短路（断电电阻接近 0）
1. **先和好板比**：同一个点、同一种表笔接法
2. **想清楚是「上电前就短」还是「上电后才短」**：上电前就短，多半是连锡、锡珠；上电后才短，多半是元件被打坏
3. **压降法**：从短路的电源轨灌电流（电压 1.0 V，限流 1 A），逐点量电压，最低的地方就是短路方向。读到 0 时，**两个焊盘都量一遍**，防止点错端
4. **逐颗量两端电压**：每颗去耦电容只量它自己的两端。适合 4 层板（电源、地都是整层铜）
5. **分地隔离**：拆 0 Ω 电阻（R22：AGND↔GND，R20：GND↔PGND），确定短在哪种地上
6. **加大电流摸发热**：限流 1.5~2 A，金属性短路也能热起来；也可以滴酒精，看哪里先干
7. **拆件验证**：拆下嫌疑元件，再量还短不短。**拆下来的元件先量再扔**

### 有电压进来，但后级不工作（断路 / 虚焊）
1. **逐级量电压**：从入口往后（D1 → C11 → D4 → U6 → C19），哪一级开始掉下来，问题就在哪两级之间
2. **同一网络两个点电压差很大 → 中间断了**
3. **小心「压上去才通」的虚焊**：量焊盘铜皮或下游点，不要只量元件的金属端；通电时一边看下游读数，一边用牙签按元件
4. **先给大电容放电**：C11 对地是 OL，存着的电会让读数「看起来正常」
5. **看电源电流**：电流 0 = 后级根本没工作

### 上电操作
- 测试插线**拔掉 CAN 两根**（第 3、4 脚），只留 +24V、GND
- 缓升法：9 V、限流 0.1 A，红表笔先按在 5 V 测点上再升压
- 不确定的预期值，**拿好板实测一次**
