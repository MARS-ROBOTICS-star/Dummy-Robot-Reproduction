## 2. 已确认的阻塞项

优先级按适用阶段定义：P0 表示对应阶段放行前必须解决，P1 表示功能或可靠性问题必须纳入修复和回归；不是所有 P0 都阻塞不通电的学习工作。

### A01：Motor-42 制造包不能直接放行

**P0，阻塞 Motor-42 PCB 制造。** `1.Hardware/motor42/motor42 Gaber.zip` 中有 31 个文件和四层铜层线索，但未发现独立 NC Drill 文件；扫描包内文本也没有常见 Excellon `M48` 文件头。`Motor-42.RUL` 的内容是 `DRC Rules Export File`，不是钻孔或铣槽文件。

Motor-35、LED Ring 和 REF 的制造包可找到相应 `.TXT` 钻孔数据，CRC 检查未发现错误；**这仅证明包内有钻孔数据，不代表已通过制造审查**。REF 包同时包含根目录和 `REF_V1/` 两套输出，不能混层发送给工厂。

三类主板未发现独立、已审核的标准 CPL。IBOM HTML 含坐标线索，不等于生产贴片坐标放行。现有 Gerber、PCB 源文件、焊盘更改版归档存在版本并存，必须从一个选定的 PCB 版本重新统一导出 Gerber、钻孔、BOM、CPL，并审核坐标原点、角度、正反面和 Pin 1。

证据：`archive_members.json`；`evidence_checks.json` 的 `gerber_packages`；`1.Hardware/motor42/`、`1.Hardware/motor35/`、`1.Hardware/ref-controller/`。

**P0，阻塞六轴运动参数冻结与全量采购。** 主审直接查看了 `6.Docs/DH参数/dummy V2 版本 DH参数.png`，发现旧方案漏掉了几何尺寸与方向位冲突。

| J1～J6 减速比 | 30 / 30 / 30 / 24 / 30 / 50 | 50 / 50 / 50 / 50 / 50 / 5 | 均不是实物验收值；J6 尤其不能误抄 |
| J1～J6 inverse | true / false / true / false / true / true | false / true / true / true / true / true | 逐轴低风险核对方向 |
| J2 软件范围 | -73～90° | -75～90° | 与选定机械及线束空间复核 |
| J3 软件范围 | 35～180° | 0～180° | 同上 |

源码证据：`2.Firmware/dummy-ref-core-fw/Robot/instances/dummy_robot.cpp:23-32`。图片展示的是六个求解器几何常量和关节配置，不能把这六个长度直接称为完整标准 DH 参数表。

主审补读 `mini11_parameters.JPG`、`mini8_parameters.JPG`，确认两张图确实都列有 30 和 50 两档减速比。它们证明“有这些型号”，不证明本项目应购买哪一档。STEP 的 `minif-11-50` 等名称是选择线索，不是实物铭牌或总传动比验收记录。

### A03：线束版本与观察方向必须逐针核验

**P0，阻塞上电。** 使用指南文本写“REF to J1 同向线，交换中间两根 CAN 线；其余为反向线”，而其他接线 PDF 只写方向，不包含同等详细说明。主审补读三页引脚图确认：电机板 P1/P2 是功率和 CAN 链路，P3 是 UART/SWD 调试接口，外观相似但功能不同。

不能把“中间两针”“左边”“同向”作为跨版本通用配线规则。必须以**同一板版本、同一观察方向**的原理图和实板为准，逐针测出 24 V、GND、CAN_H、CAN_L，再制作两端映射。两根并联供电线也要分别测通断，不能只检查其中一根。

证据：`dummy使用指南v1.3.pdf` 第 1～3 页；`6.Docs/Cable_connection.pdf`；`6.Docs/Pins definations.pdf` 第 1～3 页及 `extracted/pins-1.png`～`pins-3.png`。未完成网表/实板核验前，本文不提供统一六针编号替代原图。

### A04：电机 UART 是会改变控制模式的运动入口，不是只读调试口

**P0，阻塞首次运动。** `interface_uart.cpp:8-44` 中 `c/v/p` 分别以 A、转/秒、电机轴绝对转数为单位，内部转换为 mA 或 51200 计数/圈。命令会切换 `requestMode`，因此 `enableMotorOnBoot=false` 不构成独立的运动授权门。

同函数忽略 `_len`，依赖 `strtok/atof`，没有检查空参数、完整数字、有限值或尾部垃圾。USART IDLE 回调在中断上下文调用它，不能把 DMA 空闲边界当成可靠的文本消息协议。需要有界缓冲、消息边界、严格数值转换和显式 ARM/STOP 门。

证据：`2.Firmware/dummy-42motor-fw/UserApp/protocols/interface_uart.cpp:8-44`；`Core/Src/stm32f1xx_it.c:374-389`；`Ctrl/Motor/motor.cpp:147-150,555-583`。相同问题适用于 Motor-35。

### A05：编码器有效性与失联保护没有闭合到安全状态

**P0，阻塞首次运动。** `mt6816_base.cpp:25-56` 读到了 parity 与 `noMagFlag`，但失败时仍沿用旧角度；`motor.cpp:96-118` 的休眠条件没有接入传感器健康状态。不能把“校准表有效”当成“当前磁铁和 SPI 正常”。

普通 UART/CAN 电流、速度、位置控制路径未见通用命令存活超时停机。轨迹跟踪器某模式的超时不等于所有模式的看门狗。`main.cpp:50-56` 默认关闭堵转保护，且启动时强制关闭温度监视。默认 1 A 控制限流与 2 A 校准电流分别存在，修改一个不会自动约束另一个。

要求：传感器连续错误/无磁/采样过期触发锁存故障；命令失联由节点本地检测；恢复通信后不能自行重新运动；电流、校准、温升单独验证。带载关节应先考虑断电坠落，不能把“失能”机械地等同于“安全”。

证据：`2.Firmware/dummy-42motor-fw/Ctrl/Sensor/Encoder/mt6816_base.cpp`；`Ctrl/Motor/motor.cpp`；`UserApp/main.cpp:34-70`；`UserApp/protocols/interface_can.cpp`。

### A06：Flash 存储地址存在，但链接器未保护保留区

**P1，增加遥测和安全功能前处理。** 校准表位于 `0x08017C00`，长度 32 KiB；参数区位于 `0x0801FC00`，长度 1 KiB。程序从 `0x08000000` 开始，校准区之前只有 95 KiB，而链接脚本仍授权整个 128 KiB Flash。

应把程序可用 Flash 限定到正确边界或加入链接断言，且检查 `.data` 的 Flash 加载地址，不只检查 `.text` 大小。下载工具也必须保留校准/参数区域；全片擦除后需要重新建立参数与校准。

证据：`2.Firmware/dummy-42motor-fw/Port/Platform/Memory/stockpile_config.h:82-89`；`STM32F103CBTx_FLASH.ld:62-66`；`Port/mt6816_stm32.h`。未编译，当前固件实际尺寸未知。

### A07：`!STOP` 不是真正急停，而且触及零位移除零路径

**P0，阻塞 REF 运动。** `EmergencyStop()` 调用“移动到当前位置”，随后置主控 `isEnabled=false`、清队列，没有调用节点失能接口。`MoveJ()` 在目标等于当前位置时 `maxAngle=0`、`time=0`，后续速度计算出现 `0/0` 路径；非法浮点值可能进入 CAN 下发路径。速度零值也是必须处理的边界。

`MoveJoints()` 自身不等待到达；无限等待实际位于 `Homing()`、`Resting()` 和部分命令处理路径。发送路径还有无限信号量等待，故“收到 STOP 字符串”不代表命令已经到达电机。

要求：急停路径独立于正常运动规划，停止目标更新、清队列、设置节点安全状态，并有本地失联保护和物理功率切断兜底；不能将 `SetEnableTemp(false)` 当作失能，它是温度监视相关接口。

证据：`2.Firmware/dummy-ref-core-fw/Robot/instances/dummy_robot.cpp:60-100,232-257,402-409,458-459`；`Robot/actuators/ctrl_step/ctrl_step.cpp:22-50`。

### A08：CAN 长度、节点与发送错误处理不足

**P0，阻塞多节点接入。** REF `can_protocol.cpp:22-32` 由标准 ID 得到 0～15 的节点编号，直接索引 `motorJ[id]`；数组只有 7 个元素，7～15 越界。反馈读取至少用到 `data[4]`，但未先验证 DLC、IDE、RTR 或有限浮点值。

电机端 `OnCanCmd()` 也忽略 `_len`，短帧可能带入旧缓冲数据。REF 发送函数以 `osWaitForever` 等待信号量，发送提交失败时未完整恢复资源；电机端 `CAN_Send()` 失败直接调用关中断死循环的 `Error_Handler()`，不能假定此时桥输出会自动归零。

要求：逐命令固定长度/白名单，使用 `memcpy` 解包并检查有限数值；广播写操作默认禁用；发送超时、bus-off、ACK 丢失、邮箱耗尽均有可回收资源的故障路径。已经断线的节点收不到主控的“失能帧”，本地保护不可省。

证据：`2.Firmware/dummy-ref-core-fw/UserApp/protocols/can_protocol.cpp:17-38`；`Robot/instances/dummy_robot.h:121`；`Bsp/communication/interface_can.cpp:116-133,237-248`；电机 `Core/Src/can.c:181-203` 与 `Core/Src/main.c:171-178`。

### A09：REF 不支持“拔掉四轴就变两轴”，IMU 阻塞也不是全系统静止

**P1，阻塞最小 REF。** 六轴发送循环与到达掩码 `0b1111110` 硬编码。`Homing/Resting` 等待缺席节点时可能永久不结束。最小系统需要活动轴集合、对应反馈掩码和超时，或先写仅调用 `CtrlStepMotor` 的独立双轴试验程序。

`Main()` 先 `InitCommunication()`、`dummy.Init()`，再无限等待 MPU6050，最后才建立控制/OLED/RGB 任务和启动 200 Hz 定时器。因此 IMU 缺失会阻止后续任务启动，**但不能断言此前通信完全未初始化或系统不可能接收危险命令**。

证据：`2.Firmware/dummy-ref-core-fw/UserApp/main.cpp:157-210`；`Robot/instances/dummy_robot.cpp:60-66,232-257,296-299`。

### A10：两种“校准”完全不同，节点 ID 也不是纯 EEPROM 配置

**P0，执行校准前。** 电机编码器校准：本地按键/电机 CAN `0x02` 触发，涉及电机转动和 32 KiB 映射表。REF `!CALIBRATION`：调用 `CalibrateHomeOffset()`，使能所有节点、调整 J2/J3 电流、两次写零偏、自动进入收拢姿态并重启，**不是**读取一组静止零位，也不等价于重新做 MT6816 线性化。

电机 `main.cpp:25-28,58` 每次启动用三位拨码覆盖 `canNodeId`。CAN `0x11` 可以修改运行时/保存字段，但下次启动仍会被拨码覆盖。第四位拨码的电气作用须查所选原理图，不可仅凭三位软件代码推定。

证据：电机 `UserApp/main.cpp:25-28,58,96-97,168-171`；REF `Robot/instances/dummy_robot.cpp:199-229`。

### A11：REF 命令解析和队列边界需专项修复

**P1，开放上位机写命令前。** `sscanf` 的返回数量未检查，局部 `node/kp/mode` 可能在解析失败时未初始化；`std::string::find` 是子串匹配，不是完整命令匹配。`MoveJ/MoveL` 的失败没有可靠传回上位机，多条路径仍回复 `ok`。

命令队列固定消息大小 64 字节，`Push()` 直接把 `_cmd.c_str()` 交给队列按固定长度复制，短字符串有越界读取风险，长字符串有截断和缺终止符风险；应显式构造有界、清零的消息结构并拒绝超长命令。ASCII 流缓冲是静态共享，多通道并发也应隔离。

`node >= 1 & node <= 6` 虽应改为清晰的 `&&`，但原式对已初始化整数的范围判断并不会按子代理所说“拒绝偶数节点”。真正风险是解析失败和未初始化值。

证据：`2.Firmware/dummy-ref-core-fw/UserApp/protocols/ascii_protocol.cpp:53-105`；`Robot/instances/dummy_robot.cpp:392-417,426-523`；`Robot/instances/dummy_robot.h:182,196`；`Bsp/communication/ascii_processor.cpp:48-79`。

### A12：ESP32 存在被展平成普通文本的链接文件及网络控制风险

**P1，阻塞 ESP32 构建；网络接入前按 P0 处理。** 例如 `2.Firmware/esp32-iot/firmware/examples/esp32/uart-bridge/main/net.c` 只有一行 `../../../uart-bridge/net.c`，实际不是符号链接，CMake 却把它作为 C 源码编译。全项目在小于 250 字节的 C/C++/头文件/JS 中扫描到 320 个相对路径文本占位文件，结果见 `evidence_checks.json`；这不是对所有文件类型的穷尽链接检测，不能把这些文件的存在当成源码齐全。

另外有空的 `dummy-iot.hex`、`esputil.zip` 和 `make` 占位文件，存在平台不匹配的工具成品。恢复引用必须在工作副本中依据真实目标路径和原始版本进行，不应对全部相对路径文本盲目批量替换。

桥接源码默认启用 TCP/WebSocket，HTTP 配置接口未见鉴权；示例 `config.json` 启用了公共 MQTT broker 和公共主题。不过源码初始 MQTT 标志为 false，实际启动是否启用取决于加载的配置，不能断言所有固件一开机必连公共 MQTT。部署前必须关闭公网/公共代理控制、加入认证授权及写命令门控。

证据：ESP32 `main/CMakeLists.txt:1-7`、`main/net.c:1`；通用 `examples/uart-bridge/net.c:6-21,177-216` 和 `config.json:1`。

### A13：上位机只作为后期接口，不能误接到 Motor-42 UART

**P1，启用上位机前。** `3.Software/simple-cli/simple-cli.py:7-20` 硬编码 macOS 端口，`start()` 循环发送 REF 命令 `!START`；它不是 Motor-42 的 `c/v/p` 测试脚本。

`CLI-Tool/run_shell.py` 有失效的路径插入和 ODrive 遗留对象，但同级确实存在 `fibre` Python 源码，因此“插入路径不存在”不足以证明 import 一定失败。Python AST 检查未发现语法错误，也不证明依赖、对象协议或运行正确。应在隔离环境中做无硬件 smoke test，再做 REF 协议测试。

DummyStudio 是 Windows Unity 成品，缺少完整可重建的 Unity 源工程。源码 `USB_DEVICE/App/usbd_desc.c:94` 的 VID 为 `0x1209`，与软件配置线索相符，不能把 VID 不匹配列为已确认缺陷；实际发现机制仍需实测。

### A14：机械材料与许可证不能凭文件名或通用常识补齐
